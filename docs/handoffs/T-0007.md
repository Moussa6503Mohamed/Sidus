# T-0007 — Original question and rubric foundation

**Status:** done / released
**Owner:** Claude Code agent
**Depends on:** T-0001 (done), T-0004 (done), T-0005 (done), T-0006 (done)

## Goal

Build private original-question and versioned-rubric infrastructure for a future Exam Mode, where
every question traces to a **verified** curriculum-map node whose approved content source still
passes the T-0006 source gate. No question text, rubric text, syllabus text, mark schemes,
past-paper content, PDFs, extracted text, diagrams, OCR output, or derivative questions are
created or seeded. No AI generation, Anthropic call, OCR, ingestion, or question derivation.

## What changed

### Database (`services/core/migrations`)

- `0012_create_questions.sql` — `questions`: `id`, `syllabus_id` (FK → `syllabuses`),
  `curriculum_map_node_id` (**NOT NULL** FK → `curriculum_map_nodes`), `response_type` (CHECK:
  multiple_choice/short_answer/structured_response), `language`, `prompt`, `status` (CHECK:
  draft/verified/retired, default draft), timestamps; indexes on syllabus/node/status.
- `0013_create_question_rubric_versions.sql` — `question_rubric_versions`: `id`, `question_id` FK,
  `version` (`CHECK > 0`), `rubric` JSONB, `max_marks` (`CHECK > 0`), `status` (draft/verified),
  `created_by`/`reviewed_by` (verified Clerk subjects), timestamps. `UNIQUE (question_id,
  version)`. **`BEFORE UPDATE OR DELETE` trigger** rejects every DELETE and any UPDATE changing
  `question_id`, `version`, `rubric`, `max_marks`, `created_by`, or `created_at` — only
  `status`/`reviewed_by`/`updated_at` may change.
- `0014_create_question_events.sql` — `question_events`: append-only audit (`question_id`,
  `event_type` CHECK over the six event types, `actor_id`, `event_time`, `changed_fields`),
  `BEFORE UPDATE OR DELETE` trigger rejecting mutation — mirrors `content_source_events` /
  `syllabus_events` / `curriculum_map_events`.

### Core Go service (`services/core/internal/question`, new package)

- `model.go` — `Question`, `RubricVersion`, `Event`, `ResponseType`, `Status`, `RubricStatus`;
  `CreateInput`/`UpdateInput`/`CreateRubricVersionInput`.
- `rubric.go` — `ValidateRubric`: the validation-safe rubric schema (non-empty bounded `criteria`
  array; unique non-blank criterion `id`; positive integer `marks`; optional non-blank
  `descriptor`; no unknown fields on document or criterion; criterion marks must sum exactly to
  `maxMarks`). Returns `ErrInvalidRubric`/`ErrInvalidMaxMarks` — never raw JSON error text.
- `store.go` — `Store` interface + domain error sentinels (`ErrNotFound`,
  `ErrRubricVersionNotFound`, `ErrUnknownSyllabus`, `ErrUnknownNode`, `ErrUnverifiedNode`,
  `ErrMismatchedNode`, `ErrUnknownSource`, `ErrUnapprovedSource`, `ErrUnlinkedSource`,
  `ErrMismatchedSource`, `ErrNoChanges`, `ErrInvalidTransition`, `ErrMissingVerifiedRubric`,
  `ErrInvalidRubric`, `ErrInvalidMaxMarks`, `ErrDuplicateRubricVersion`).
- `postgres_store.go` — `PostgresStore`: `CreateQuestion`, `UpdateQuestion`, `VerifyQuestion`,
  `RetireQuestion`, `GetQuestion`, `ListQuestions`, `CreateRubricVersion`, `ListRubricVersions`,
  `VerifyRubricVersion`. `validateGrounding` is the single gate (node exists → same syllabus →
  verified → source approved+linked+matched) and runs inside **every** write transaction before
  any row, status change, or event. Version numbers are allocated under a row lock on the parent
  question (`SELECT ... FOR UPDATE`), so they are unique and monotonic. `22P02` (malformed UUID)
  maps to the same stable domain error as a missing row.
- `handlers.go` — `Register` mounts `GET/POST /questions`, `GET/PATCH /questions/{id}`,
  `POST /questions/{id}/verify`, `POST /questions/{id}/retire`,
  `GET/POST /questions/{id}/rubric-versions`,
  `POST /questions/{id}/rubric-versions/{version}/verify`, each behind `auth.Protect`. Strict JSON
  via a shared `decodeStrict` that enforces a **case-sensitive field allowlist** per endpoint
  before the struct decode. Infrastructure failures always return the single generic
  `internal_error` message.

## Review fixes on top of `768c8e2`

Three findings from the T-0007 review. All additive: no table, column, role, permission, question
visibility rule, source-gate behaviour, Clerk setup, or unrelated package changed, and still
nothing seeded and no AI/OCR/ingestion path.

### Fix 1 — a rubric version is bound to the question content it was reviewed against

**Problem.** A draft question could gain a **verified** rubric version and then have its `prompt`,
`responseType`, `language`, or `curriculumMapNodeId` changed; `VerifyQuestion` still accepted that
rubric, i.e. one reviewed against wording the question no longer had.

**Design.**

- `migrations/0015_add_question_content_revision.sql` (additive only — `ADD COLUMN IF NOT EXISTS`,
  a re-runnable `CHECK`, `CREATE OR REPLACE FUNCTION`, `CREATE INDEX IF NOT EXISTS`; no `DROP
  TABLE`/`DROP COLUMN`, asserted by `TestMigrations_ContentRevisionIsAdditive`):
  - `questions.content_revision INTEGER NOT NULL DEFAULT 1`, `CHECK (> 0)`;
  - `question_rubric_versions.question_revision INTEGER NOT NULL DEFAULT 1`, `CHECK (> 0)`;
  - the immutability trigger now also rejects any change to `question_revision`, so no direct SQL
    rewrite can re-point a stale version at current content;
  - `(question_id, question_revision, status)` index for the verification lookup.
- `UpdateQuestion` appends `content_revision = content_revision + 1` to the same `UPDATE` as the
  content change, inside the transaction and under the existing row lock. `ErrNoChanges` returns
  before that point and every rejected write rolls back, so exactly one increment per successful
  update — never on `no_changes`, validation/grounding/strict-decode rejection, verify, or retire.
- `CreateRubricVersion` stamps `current.ContentRevision` onto the new version under the same row
  lock that allocates the version number, so a concurrent edit cannot slip between the two.
- `requireCurrentVerifiedRubric` (new, in `postgres_store.go`) counts verified versions and
  verified-at-current-revision versions in one query inside the verifying transaction.
- New domain error `ErrStaleVerifiedRubric` → **`409 missing_current_verified_rubric`**, distinct
  from `missing_verified_rubric` (nothing verified at all) because the fixes differ: append and
  verify a new version vs. review a rubric for the first time.
- Old versions are **never deleted or downgraded** — they stay `verified`, immutable, and readable
  to editorial roles; they are only stale for question verification.
- Field names added to the audit trail (names only, no values): `contentRevision` on
  `question_updated`, `questionRevision` on `rubric_version_created`.

### Fix 2 — rubric JSON keys are matched exactly and case-sensitively

**Problem.** `ValidateRubric` decoded into a Go struct. Go matches JSON field names
case-insensitively, so a schema documented as accepting only `criteria`/`id`/`marks`/`descriptor`
in fact accepted `Criteria`, `ID`, `Marks`, `Descriptor` — and, like any struct or map decode,
silently kept the last value of a duplicated key.

**Design.** `rubric.go` now validates against `encoding/json`'s token API (`decodeExactObject`)
with explicit key sets `rubricDocumentFields` = {`criteria`} and `rubricCriterionFields` =
{`id`, `marks`, `descriptor`}. It rejects: any non-exact key at any level (including case variants
and keys at the wrong level), duplicate keys, non-object criteria, `criteria: null`, non-string
ids, blank ids, duplicate criterion ids, marks that are strings/booleans/null/fractional/
non-positive/absurd, non-string descriptors, blank descriptors, trailing JSON, and a bad `maxMarks`
sum. Responses still use the existing stable `invalid_rubric` / `invalid_max_marks` codes and never
echo parser text. Explicit `descriptor: null` still means "absent", as before.

### Fix 3 — the optional node filter on `GET /questions` is validated

**Problem.** `curriculumMapNodeId` went straight into the `WHERE` clause, so an unknown or foreign
node returned `200` with an empty list — the same "a typo looks like an unauthored map" problem the
T-0006 review already fixed for `syllabusId`.

**Design.** New `validateNodeFilter` in `postgres_store.go` runs after the syllabus check: unknown
or malformed node → `ErrUnknownNode` (`400 unknown_node`); a real node of another syllabus →
`ErrMismatchedNode` (`400 mismatched_node`). It is deliberately weaker than `validateGrounding` — a
reader may filter by a node that has since been retired or whose source regressed, and gets an
empty list, not an error. Unknown/inactive syllabus behaviour is unchanged and still checked first.

## Schema decisions (also recorded in D-0009)

- **A question stores both `syllabus_id` and `curriculum_map_node_id`**, with equality enforced by
  Core on every write. Storing both keeps list-by-syllabus a single indexed read while the
  invariant stays application-enforced (a bare FK cannot express "node is verified and its source
  is still approved for this syllabus").
- **The grounding gate re-runs on every question write**, not just create — a node can be retired
  and a source can be un-approved, unlinked, or re-linked afterwards. Accepted consequence: a
  question with regressed grounding is frozen, including for retirement, until the node/source is
  restored. Same trade-off already accepted for curriculum-map nodes (D-0008 review fix 2).
- **`syllabusId` is immutable on a question**; repointing `curriculumMapNodeId` re-validates the
  syllabus match, so a cross-syllabus move is rejected rather than half-applied.
- **Rubric versions are append-only and DB-immutable.** Correcting a rubric means a new version.
  This is what makes a marked answer explainable by the exact rubric that produced it, and what
  makes the `rubric` component of the D-0003 explanation cache key well-defined.
- **Version numbers are server-allocated under a row lock**, never caller-supplied (no races, no
  gaps, no overwriting history). The unique index is the backstop → `duplicate_rubric_version`.
- **A question cannot be verified without a verified rubric version** (`409
  missing_verified_rubric`); a draft rubric does not count.
- **`status` is never PATCHable** — only verify/retire change it, so lifecycle rules live in one
  place.
- **Rubric listing has its own permission** (`question_rubric:read`) rather than reusing
  `question:read`, because it exposes draft rubric structure.

### Hardening beyond the curriculum-map precedent

`decodeStrict` now enforces a case-sensitive allowlist on **`POST` as well as `PATCH`**. Go's
struct decoding matches JSON field names case-insensitively, so `DisallowUnknownFields` alone
accepts `{"SyllabusId": ...}` as `syllabusId`; the allowlist is the only place that rejects a case
variant. (Verified by test: `TestCreateQuestion_StrictJSON/case_variant` fails with the allowlist
removed.) The `POST` paths in `curriculummap`/`contentsource`/`catalogue` still rely on
`DisallowUnknownFields` alone and therefore still accept case variants of known fields — a
pre-existing, cross-package observation, not fixed here (see "Blockers / open questions").
