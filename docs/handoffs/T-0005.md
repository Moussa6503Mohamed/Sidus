# T-0005 handoff

**Status:** review
**Owner:** Claude Code agent
**Depends on:** T-0001 (done), T-0002 (done), T-0003 (done), T-0004 (done)

## Goal

Let an editor/admin explicitly confirm and establish a missing or stale
`content_sources.catalogue_syllabus_id` link through the existing authenticated `PATCH
/content-sources/{id}` flow, without a direct database workaround and without changing what a
caller may submit in the request body.

## Problem

Migration 0008 (T-0004) added `content_sources.catalogue_syllabus_id` and deliberately left every
existing row's FK `NULL` — no silent auto-mapping. The pre-T-0005 `PATCH` diff logic in
`PostgresStore.Update` compared `syllabusCode` (and every other updatable field) purely as a
single-column value diff: if the supplied code text matched what was already stored, the request
was `400 no_changes`, even though `catalogue_syllabus_id` was still `NULL`. No safe
application-layer path existed to complete the link.

## Delivered

### Core (`services/core/internal/contentsource`)

- `postgres_store.go`:
  - `columns()` (the generic per-field diff helper) no longer includes `syllabusCode` — it is
    handled separately since it can affect two columns (`syllabus_code`,
    `catalogue_syllabus_id`) independently.
  - New `stringPtrEqual` helper (nil-safe optional-string equality).
  - `Update` now diffs `syllabusCode` text and the resolved `catalogue_syllabus_id` separately:
    - **Text code differs from stored** → both `syllabus_code` and `catalogue_syllabus_id`
      updated; `changed_fields` records `"syllabusCode"`.
    - **Text code matches stored, resolved FK differs from stored** (including a `NULL` stored
      FK) → `catalogue_syllabus_id` updated alone; `changed_fields` records
      `"catalogueSyllabusId"` — never `"syllabusCode"`.
    - **Text code matches stored, resolved FK matches stored** → unchanged `400 no_changes`
      behavior (no write, no event).
  - No change to the handler layer, resolver, request/response shape, permission checks, or the
    `syllabusCode` unknown/inactive/ambiguous `400` path — all unchanged from T-0004.
- `handlers_test.go`: `memoryStore.Update` (the in-memory test double) mirrors the identical
  split-diff logic so handler tests exercise the same semantics without a live database.
- New tests (`handlers_test.go`):
  `TestUpdate_SameCode_NullCatalogueLink_LinksProvenance`,
  `TestUpdate_SameCode_StaleCatalogueLink_Relinks`,
  `TestUpdate_SameCode_MatchingCatalogueLink_NoChanges`,
  `TestUpdate_DifferentCode_UpdatesCodeAndCatalogueLink`,
  `TestUpdate_CatalogueLinkConfirmation_LearnerDenied`.
- New integration test (`postgres_store_test.go`):
  `TestPostgresStore_Integration_ProvenanceCatalogueLinking` — against a disposable database,
  proves: null-FK link, no-op re-confirmation (`no_changes`, no second event), stale-FK safe
  relink, and a genuine code change updating both columns with `["syllabusCode"]` audit. Also
  confirms the resulting `content_source_events` row is immutable (UPDATE rejected by trigger),
  consistent with every other event in this table.

### No changes

- No migration. No schema change. `catalogue_syllabus_id` (T-0004, migration 0008) is reused

- No new endpoint, no handler changes, no contract (`packages/shared`) changes — the request

## Manual steps (human, not performed by this task)

The two content-source rows seeded by migration 0003 remain `catalogueSyllabusId: null` after
this change. An editor/reviewer/admin must call, per row:

```
PATCH /content-sources/{id}
{"syllabusCode": "0610"}   // and separately "5090" for the other row
```

This is documented in `docs/provenance-catalogue-linking.md` ("Manual steps for the two seeded
sources"). T-0005 adds the safe, audited path — it deliberately does not perform the linking
itself, matching D-0007's original refusal to auto-map ambiguous rights records.
