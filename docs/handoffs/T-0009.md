| Next.js route | Method(s) exported | Core operation |
| --- | --- | --- |
| `app/api/editorial/content-sources/route.ts` | `GET`, `POST` | list / create |
| `app/api/editorial/content-sources/[id]/route.ts` | `GET`, `PATCH` | get / update |
| `app/api/editorial/content-sources/[id]/approve/route.ts` | `POST` | approve |
| `app/api/editorial/content-sources/[id]/reject/route.ts` | `POST` | reject |

`405` structurally, not a runtime check.

## Auth and fail-closed behavior

- Core stays the sole authorization authority (D-0006 unchanged): every proxied mutation is
  still gated by Core's existing `auth.Protect` (401/403). The web-side role check
  (`lib/editorial/permissions.ts`/`role.ts`) only decides which controls render.
- `callCore` fails closed, in order: `SIDUS_CORE_API_URL` missing/blank → `503
  service_unavailable` (no auth check, no network call) → missing/expired Clerk session token
  → `401 unauthorized` (no network call) → invalid `{id}` (`^[A-Za-z0-9_-]{1,128}$`) → `400
  invalid_id` (no network call).
- The bearer token is obtained via `auth().getToken()` and forwarded only in the
  `Authorization` header of the server-side `fetch` to Core; it is never logged, echoed, or
  returned to the browser through this layer.
- A `fetch` failure maps to a generic `502 upstream_unavailable`; a non-JSON/unparsable Core
  response maps to a generic `502 upstream_error`. Neither ever forwards the underlying error
  text, stack trace, or target URL. No `console.*` call exists anywhere in `lib/editorial/*` or
  `app/api/editorial/*`.
- `POST`/`PATCH` bodies are validated (`application/json`, ≤100 KB, syntactically valid JSON)
  and forwarded **verbatim** (raw text, never re-serialized); the approve route always sends a
  fixed `{}` regardless of any client-supplied body.

## Decisions / assumptions

See `D-0011` in `docs/decisions.md` for the full architecture decision (closed operation
union vs. generic proxy, raw-body passthrough, fail-closed ordering, UI-only role check,
server-rendered nav gating). Notable assumptions carried in `docs/tasks/active.md`:
`SIDUS_CORE_API_URL` is a new server-only env var analogous to `DATABASE_URL`; Vitest/Testing
Library were added since the web app had no test runner; `packages/shared` is wired in via a
`tsconfig`/`vitest` path alias rather than npm workspaces (none exist in this repo).

`app/layout.tsx` became an `async` Server Component (it now calls `auth()` to decide nav
visibility), which makes the home page dynamically rendered instead of statically generated —
a minor, expected behavior change with no functional impact (confirmed by the build's route
listing, all routes already render on demand).
