## Decisions / assumptions

- **`127.0.0.1:443`, not a non-standard port.** Confirmed with the user before implementation
  (see D-0022 and the plan's Context section): the T-0022 client's `_canonicalize_base_url` has
  an existing, explicitly tested contract rejecting any non-default-port HTTPS origin. Loopback
  `443` keeps `SIDUS_CORE_API_URL=https://127.0.0.1` valid against that unchanged validator.
- **Manual openssl CA, not mkcert / system trust-store install.** Keeps everything scoped to one
  private directory; no admin rights, no machine-wide trust-store mutation for a throwaway stack.
- **Postgres and Core publish no host port at all** — only the proxy does, and only on
  `127.0.0.1`. Minimizes exposure beyond what the task requires.
- **My own automated validation used a scratch, gitignored `.env.local-import` with
  syntactically-valid-but-fake `CLERK_SECRET_KEY`/`CLERK_JWT_ISSUER`** (never a real secret) —
  sufficient for Core's `buildVerifier` to mount the auth-gated routes and prove fail-closed
  behavior (401 with no token) without needing a genuine Clerk session. That scratch file was
  deleted after validation completed; it was never staged (`git status --short` never listed it,
  confirmed via `git check-ignore -v` before use).
- **The Windows-curl `--ssl-no-revoke` caveat** is a Schannel-only artifact of testing with
  Windows-native `curl.exe` against a CA with no CRL/OCSP endpoint (normal for a throwaway dev
  CA). It does not affect the actual T-0022 Python client, which never performs revocation
  checking. Documented in the guide so a Windows operator isn't confused by it later.
- **One-record smoke test and the full 489 `--apply` were not executed**, per the task's
  explicit constraints — only documented.
