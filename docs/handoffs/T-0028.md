# T-0028 — Learner Module selection and availability-aware count

## Status

Review. Not pushed or released.

## Delivered

- Added `GET /learner/modules?syllabusId=...` in Core under existing
  `learner_question:read`. The hand-written learner-safe module projection has only `id`,
  `syllabusId`, `code`, and `label`.
- Module discovery applies question delivery's live eligibility conditions. Only a verified
  curriculum entry with at least one currently eligible question appears; source metadata,
  locators, lifecycle fields, provenance, parents, and rubrics remain unavailable.
- Added one closed learner BFF operation and fixed same-origin route:
  `GET /api/learner/modules?syllabusId=...`. Missing/invalid ids fail before Clerk/Core access;
  existing missing config/token, redirect refusal, and Core-5xx sanitization remain unchanged.
- Practice and Exam now show human-readable **Module** selectors with an All modules choice;
  raw curriculum identifiers are removed from learner UI.
- Practice and Exam now use All available by default or one positive learner-entered count.
  Counts above current availability, zero, invalid, or fractional values are blocked with an
  availability message. No hard 10-question cap or silent truncation remains.

## Scope boundaries

- No migrations, source/private files, runtime records, question content, response-type changes,
  marking rules, source/provenance disclosure, or auth-policy changes.
- Existing learner list response still carries the internal `curriculumMapNodeId` contract field
  for API compatibility, but learner UI does not expose its name or ask users to enter it.
- Current deterministic delivery/attempt submission remains MCQ-only. Multi-response support is
  explicitly deferred to the separate response-type audit/work item.
